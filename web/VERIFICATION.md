## Frontend findings (Phases 1–5)

| # | Finding | File(s) | Severity | Fix applied |
|---|---|---|---|---|
| 6 | Tailwind v4 collision: the design token file's spacing scale (`--spacing-4` … `--spacing-96`) is named by its own pixel value, but Tailwind v4 reserves `--spacing-N` for its dynamic multiplier scale (`--spacing-8` normally means "8 × 4px = 32px"). Copying the token file's spacing block verbatim silently broke every height/width/padding/gap utility sharing a number with the token list — `h-10` rendered at 10px, not 40px. Caught via `getComputedStyle` in the browser, not by reading the CSS. | `web/src/app/globals.css` | Would have broken sizing on every component built afterward | Omitted the token file's spacing keys from `@theme`; Tailwind's native dynamic scale already reaches every one of those exact pixel values under its own numbering. |
| 7 | `SlideOver` autofocused its own close button instead of the first form field, because the close button precedes the form in DOM order and the focus query scoped to the whole panel (header included). Violates §7.7/§8's explicit "first field autofocused." Caught by reading `document.activeElement` after opening the panel, not by eyeballing. | `web/src/components/ui/SlideOver.tsx` | Every slide-over (task create/edit) shipped the wrong initial focus | Scoped the autofocus query to the body-content ref, excluding the header; the full-panel ref is still used for the Tab-trap boundary. |
| 8 | **The big one.** `fetchFromNestForRSC` and the generic BFF proxy both gated their refresh-on-401 retry on `if (status === 401 && accessToken)`. Once the `mt_at` cookie's own ~15-minute maxAge elapses, the browser stops sending it entirely — so `accessToken` is `undefined`, the condition is false, and the code gave up immediately instead of attempting a refresh, even though a perfectly valid 7-day `mt_rt` was sitting right there. Every RSC page (`/dashboard`, `/settings`, `/admin`) and every client-side mutation would have hard-failed with "No token provided" exactly when the access token expired — the one moment the whole refresh-token architecture exists to handle gracefully. Found by walking the real UI for ~15 minutes straight and watching `/settings` throw into the `error.tsx` boundary; reproduced and confirmed via console (`ApiError: No token provided` inside `<SettingsPage>`). | `web/src/lib/server/rsc-fetch.ts`, `web/src/app/api/bff/[[...path]]/route.ts` | **Critical — silent session death after ~15 minutes of otherwise-normal use** | Dropped the `&& accessToken` condition from both call sites; `refreshSession()` already handles a missing refresh token gracefully on its own, so the extra gate was only ever wrong, never protective. |
| 9 | A 6-card `useReveal` scroll animation could get permanently stuck at `opacity: 0` — `IntersectionObserver` is frame-driven, and a fast/large scroll jump (spacebar, PageDown, a hard trackpad flick) can in principle move past an element's whole intersecting window between two rendered frames, so the callback never fires. Reproduced live: after one large programmatic scroll, 4 of 6 feature cards stayed invisible indefinitely. | `web/src/hooks/useReveal.ts` | Content could vanish permanently depending on how a visitor scrolled | Added a 1.2s fallback timer that forces `visible = true` regardless of the observer, plus a more generous `rootMargin` so the observer fires earlier in the common case. |
| 10 | **Systemic.** `tailwind-merge`'s default config doesn't recognize this project's custom type-scale names (`text-caption`, `text-body`, ...) as font-size utilities. Lacking that, it fell back to treating every unrecognized `text-*` suffix — including color utilities like `text-ink-black` — as one ambiguous group and kept only the last one written, silently deleting the other from the rendered class list (confirmed directly: `twMerge("text-ink-black text-body")` → `"text-body"`, color gone). This is root-cause for `cn()`, used everywhere — `Button` and `Badge` both build their classes via `cva()` combining a color variant with a size class, so **every button and every status badge in the app had its explicit text color silently dropped**, falling back to whatever color it happened to inherit. It went unnoticed through most of this build because the inherited fallback (`body`'s `ink-black`) coincidentally matched most buttons' intended color anyway — it only became visible when a footer button inherited `parchment-cream` from a dark ancestor instead, rendering white-on-white. Confirmed the fix closes it for badges too (each status tone now carries its own distinct, correct color). | `web/src/lib/utils.ts` | **Critical, and silent** — every button and badge in the app was one inherited-color coincidence away from being unreadable | Configured `extendTailwindMerge` with this project's `font-size` scale as its own class group, so it no longer competes with `text-color` for the same slot. Fixed at the single shared `cn()` call site rather than patched per component. |
| 11 | **Widespread color-contrast failures**, caught by a real Lighthouse run against a production build, not assumed: (a) `--color-ash-gray` (`#99978f`) only reaches 2.4–2.9:1 against this palette's light surfaces — nowhere close to WCAG AA's 4.5:1 — yet it was used for roughly 20 pieces of real body/caption text across the app; (b) `--color-slate-warm` (`#7a7974`), which `DESIGN-3.md`'s own accessibility note recommends as Ash Gray's *replacement*, only reaches 4.36:1 on white and 4.07:1 on parchment cream — both still under 4.5:1, so the documented fix was itself still failing, just less obviously; (c) `Badge`'s colored-text tones (`text-burnt-orange`, `text-deep-teal`, `text-forest-green`, `text-magenta-bloom`) each fail against their own tinted backgrounds (as low as 2.93:1) — these were never in `DESIGN-3.md` at all, which specifies plain Ink Black text on accent-card backgrounds; (d) `--color-coral-red` itself (`#ee5968`) only reaches 3.35:1 on white, below 4.5:1, affecting `FieldError`, the destructive button variant, and the destructive dropdown-item text. | `web/src/app/globals.css`, `Badge.tsx`, `FieldError.tsx`, `Button.tsx`, `DropdownMenu.tsx`, `Tabs.tsx`, `Card.tsx`, `Toast.tsx`, `EmptyState.tsx`, `ShortcutsSheet.tsx`, `Input.tsx`, `Textarea.tsx`, `Select.tsx`, `TaskCard.tsx`, `TaskColumn.tsx`, `TasksBoard.tsx`, `DashboardContent.tsx`, `Sidebar.tsx`, `SessionCard.tsx`, `StackBar.tsx`, `HowAuthWorks.tsx`, `Hero.tsx`, `TaskBoardPreview.tsx`, `SecuritySection.tsx`, `PasswordStrengthMeter.tsx`, and every auth/status page | **Real accessibility failures, not just a Lighthouse-score exercise** | Added `--color-coral-red-text` (`#be4753`, the same hue scaled to clear 4.5:1) for error/destructive text specifically. **There is no "resend verification email" feature — built one.** The user asked for this directly, and it was missing on both ends: `AuthController` had no route for it, and both `check-email` and the expired-token branch of `/auth/verify` told users to *"register again with the same email"* to get a new link — which doesn't work, since `register()` 409s on an existing account. Added:
- Backend: `POST /auth/resend-verification` (`ResendVerificationDto`, `AuthService.resendVerificationEmail`), rate-limited to 3/minute (tighter than the 100/minute global default, matching login's own dedicated throttle) since each call triggers a real, cost-bearing email send.
- Frontend: `ResendVerification` component (one-click when the email is already known, on `check-email`; a small inline email form when it isn't, on the expired-link branch of `/auth/verify`), a BFF route at `/api/auth/resend-verification` that mirrors `forgot-password`'s enumeration hardening — an unknown-email 404 *and* an already-verified 400 both normalize to the same neutral success response, so this endpoint can't be used to probe whether an address is registered or already verified.
- Verified live end-to-end through the real UI: register → land on `/auth/check-email` → click "Resend verification email" → green "New link sent" confirmation → confirmed via the backend log and a temporary debug print (removed after) that Resend returned a real message ID for the resend call too, not just the original registration email.

**Known account-level constraint, not a code bug:** the project's Resend API key is on a very restricted plan — response headers show `x-resend-daily-quota: 2` and `x-resend-monthly-quota: 2`. Once the code fix above is in place, delivery still depends on this quota: Resend's sandbox also rejects `to` addresses on placeholder domains like `example.com` outright (a real, deliberate Resend safety check, confirmed via their own `422 validation_error` response), and will only deliver to the Resend account's own verified address (or `delivered@resend.dev`, Resend's dedicated always-succeeds test inbox) until a real sending domain is verified on that account. This is worth knowing before assuming any further "email didn't arrive" report is a code issue.

**Confirmed live:** a follow-up report ("still not arriving," tested against `ankuu.tech@gmail.com`) reproduced exactly this — Resend's own 403 response named the one address it will actually accept: `You can only send testing emails to your own email address (ankitsingh9891996765@gmail.com)`. Re-sent to that address and got back a real message ID with `error: null`, closing the loop: the send pipeline is correct, and delivery to any other address requires verifying a domain at resend.com/domains (not a code fix).

**Branded HTML email templates.** All three transactional emails (`verify`, `forgot-password`'s reset link, and a new post-reset confirmation) were plain unstyled `<h1>`/`<p>` strings — no branding, no Passionfroot palette, nothing matching the actual product. Added `src/auth/email-templates.ts`: one shared table-based, inline-styled shell (the layout email clients — especially Outlook's Word rendering engine — can actually render consistently; flexbox/grid and most `<style>` rules don't survive there), instantiated three times with a distinct accent color and copy per flow: Deep Violet for verification (welcoming), Twilight Indigo for the reset-password link (more serious), and a darkened Forest Green for the new password-changed confirmation. That last color needed the same fix already applied to `--color-coral-red-text` elsewhere in this project — plain `--color-forest-green` (`#00a63e`) only reaches 3.22:1 against white, under WCAG AA's 4.5:1; darkened the same hue to `#007a2e` (5.47:1) for any text use. Also added `AuthService.sendPasswordChangedEmail`, wired into `resetPassword()` — the app previously reset a password with zero notification to the account owner, a real gap for a security-sensitive action. Verified: rendered all three templates to static HTML and reviewed them in a real browser (not just read as strings), then exercised the actual send path for all three — register (verification), forgot-password (reset link), and a full reset-password round trip using a token read directly from the database — against `delivered@resend.dev`, with zero Resend API errors on any of the three.

**Resend replaced with Nodemailer + Gmail SMTP.** The user needed real delivery to arbitrary recipients without paying for a domain (Resend's sandbox restriction — see above — only lifts once a domain is DNS-verified on Resend, which costs money even though Resend itself is free). Gmail's own SMTP relay has no equivalent restriction: sending through an already-real, already-trusted personal account needs no domain verification at all, at the cost of Gmail's own sending limits (~500/day on a free account) and a marginally higher spam-filter risk than a dedicated ESP with a verified domain — both acceptable at this project's scale. Swapped `Resend` for `nodemailer` in `src/auth/email.service.ts` — same three method signatures (`sendVerificationEmail`, `sendResetPasswordEmail`, `sendPasswordChangedEmail`), same imported templates from `email-templates.ts` (untouched, per explicit instruction), only the transport changed. `EMAIL_FROM` (a separately-configurable address) is gone — Gmail requires the envelope `from` to equal the authenticated account or a verified alias, so it silently rewrites or rejects anything else, and letting it drift out of sync with `SMTP_USER` was a needless foot-gun; the `from` header is now derived from `SMTP_USER` directly (`"MyTask" <SMTP_USER>`). Added a startup `Logger.warn` in `EmailService`'s constructor when `SMTP_USER`/`SMTP_PASSWORD` are unset — this project has now hit the "a misconfigured mail sender fails completely silently" bug twice (see finding #12); a loud, actionable log line the moment it boots misconfigured is cheap insurance against a third occurrence. Verified in two passes. First, without real credentials: backend boots and logs the expected warning; a resend-verification call still returns its normal success response to the caller (matching existing behavior) while the real send fails with a caught, logged `EAUTH` error and does **not** crash the process — confirmed the server stayed up and serving afterward. Second, once the user supplied a real Gmail App Password: re-tested live against `ankuu.tech@gmail.com` — the exact address Resend's 403 had blocked earlier in this same session — for both the verification email and the forgot-password reset-link email. Confirmed via Nodemailer's own send result, not just an absence of a thrown error: `response: "250 2.0.0 OK ... gsmtp"` (Gmail's SMTP success code), `accepted: ["ankuu.tech@gmail.com"]`, `rejected: []`. The original problem — real users' emails never arriving — is fully resolved.
